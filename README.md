# nixos-config

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

NixOS for all my stuff!

## Layout

```
flake.nix              auto-generated by flake-file -- do not edit
outputs.nix            flake-parts entry point
hosts/                 one directory per machine, each with host.nix
homes/                 per-user Home Manager configurations
  ar175/
  mom/
modules/
  tree/
    module.nix           declares the `hosts` option, builds every machine
    hosts.nix            imports hosts/
  repository/           flake-file input declarations
  options/              the option surface: device, profiles, programs, system
  core/
    common/             always on for every host
    roles/              graphical, workstation, laptop -- imported per host
    profiles/           workstation, gaming -- software bundles
  system/               boot loader, doas, opt-in programs (dirs when they need data)
  hardware/             audio, bluetooth, gpu, power, adb, ...
```

Each account selects a Home Manager entry point from `homes/<username>/` through
its `homeModules` setting in the host definition. User programs and settings are
kept with that account rather than shared through a NixOS module.

Assets used by a system program live beside it, e.g.
`modules/system/programs/noctalia/assets/`.

Files under `modules/` whose names start with `_` hold shared configuration
or data and are skipped by import-tree. Flake-level package modules such as
`system/programs/neovim/_package.nix` are imported explicitly by `outputs.nix`.

## Machines

Machines are entries in the `hosts` option, one directory each under `hosts/`,
listed in `hosts/default.nix`. Each contributes a `host.nix`; the directory can
hold more (a kernel, a filesystem layout, per-concern modules) without changing
anything else. Adding a machine is a new directory plus one line. For example, here is my `apollo` host:
```nix
{flakeRoot, ...}: {
  hosts.apollo = {
    enable = true;
    hostName = "apollo";
    stateVersion = "26.05";

    users.ar175 = {
      shell = "zsh";
      extraGroups = ["wheel" "video"];
      homeModules = [(flakeRoot + /homes/ar175/home.nix)];
    };

    roles = ["graphical" "workstation" "laptop"];

    features = {
      modules.device.hasSound = true;

      modules.profiles = {
        workstation.enable = true;
        gaming.enable = false;
      };
    };
  };
}
```

There are three axes, and they answer different questions:

- **`modules.device.*`** is capability: what hardware this machine has.
- **`roles`** is identity: what the machine *is*. Each role names a directory
  under `modules/core/roles/`, and every module in it is imported for that host
  only. Role code is unconditional -- a graphical machine simply has a session.
- **`modules.profiles.*` / `modules.system.programs.*`** is system software.
  Profiles enable NixOS program bundles with `mkDefault`, so a host can turn a
  system program back off. Per-user programs are configured separately under
  `homes/<username>/`.

`users` is keyed by account name; each entry creates a system account and a
Home Manager generation. `homeModules` selects that account's configuration, so
different users can have different programs and settings. Keep those modules in
`homes/<username>/`.

`features` is inserted into the system as a module, so `lib` and `pkgs` are in
scope inside function modules used there.

| Host | What it is |
|---|---|
| `apollo` | the workstation: Plasma and Niri sessions, Noctalia Greeter, NVIDIA; gaming profile off |
| `iso` | Calamares installer, plays the `graphical` role |

The gaming profile controls the system gaming bundle (Steam, Bottles, and
qBittorrent). Minecraft is configured separately in ar175's Home Manager setup,
so it remains installed while that profile is off.

## How it fits together

The option surface lives in `modules/options/` and is imported into **every**
host. The modules under `core/common`, `core/profiles`, `hardware` and `system`
are too; roles are the only per-host imports. A module that only affects some
machines owns no option of its own -- it reads one of the central options and
wraps its config in `lib.mkIf`:

```nix
{
  lib,
  config,
  ...
}: let
  cfg = config.modules.system.programs.gaming;
in {
  config = lib.mkIf cfg.enable {
    programs.steam.enable = true;
  };
}
```

Adding a feature never requires touching `hosts/default.nix` to import it --
the module is already in every system, waiting on its option. Only a role (a
new *kind* of machine) is new plumbing.

### Three things that are not obvious

- **`imports` must be a concrete list.** `lib/modules.nix` runs `imap1` (and so
  `length`) over it, so `imports = lib.mkIf ...` is a type error. Only `config`
  can be gated.
- **Option and implementation are split on purpose.** Declarations live in
  `modules/options/`; implementations read them from anywhere. The option
  surface is one readable list, and `rg "programs.gaming"` finds every user of
  an option and its single declaration.
- **A plain attrset module has no arguments.** To use `pkgs` or `lib` inside a
  value that becomes a module, write it as `{pkgs, ...}: {...}`.

### Cross-cutting modules

- Wrapped applications (`pkgs.myTerminal`, `myYazi`, `myTmux`, `myNoctalia`)
  come from `nixpkgs.overlays`, so they are reachable as `pkgs.*` from any
  module. They used to be built in a flake-parts `perSystem` block, which forced
  every consumer through `self.packages.${system}.myX`.
- Home Manager configuration is selected explicitly for each account through
  `homeModules`; it lives under `homes/<username>/` and does not use a shared
  NixOS program switch.
- `outputs.nix` passes `flakeRoot` as a special argument. Use
  `flakeRoot + /path/from/repository/root` for paths that cross directories;
  avoid parent-relative imports.

## Partitioning

The on-disk layout is declared in `hosts/apollo/fs.nix` as plain
`fileSystems`. disko was never wired up -- its layout file was imported by
nothing -- and has been removed.

## Verifying a change

Comparing derivation paths is the only trustworthy check that a config change
did not alter anything:

```bash
nix eval .#nixosConfigurations.apollo.config.system.build.toplevel.drvPath
```

An identical path means the system definition is unchanged.

## Regenerating flake.nix

`flake.nix` is generated from the input declarations in `modules/repository/`:

```bash
nix run .#write-flake
```
